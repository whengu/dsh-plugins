# dsh-auto-continue — 需求保留，实现已删除

**状态：本目录只保留需求文档（[requirement.md](requirement.md)）。实现代码与配套文档已全部删除。**

删除日期：2026-11-19

## 为什么删除

实现（`dsh-plugins/dsh-auto-continue/`，host + client 双半边）在真机上引发了**服务级故障**，因此连同代码、评审与进度文档一并删除，不作为可用插件保留。

### 现象

启用该插件的 Host 启动后，整个进程失去响应：连「无 token 直接返回 401」这种本地快速路径都挂死、返回零字节，浏览器无法访问页面。用 `--patch` 禁用该插件、其余条件完全相同的对照实例则一切正常，请求毫秒级应答。两者唯一差异就是本插件，据此确认肇事者。

同时观察到该进程对 LLM 网关出现 CLOSE_WAIT——请求已发出、被远端掐断，本地未清理。

### 机制根因

插件对判定为「崩溃残留」的会话执行了两个动作：

1. `ctx.agents.resume({ resumeSessionId })` —— 恢复会话
2. `handle.agent.followup(建议消息)` —— 排入一条 user 消息

`followup` 的语义是「排入下一条消息并**唤醒一轮**」(`dsh-agent-loop` 的 `send(input, "next-turn", true)` → `wakeDriver()` → `kick()` → `turn()`)。也就是说，插件启动后会自动让模型**凭空跑一整轮推理**：调 LLM、执行工具，而此刻没有任何用户在场。

这构成三个叠加的缺陷：

- **无人值守的自动推理**：没有用户处理工具审批、流式输出与失败恢复；LLM 网关断开后连接残留，把进程拖垮。
- **自触发死循环**：崩溃残留会话的尾部是一座未闭合的 `turn/start`，它不会因为插件跑过一次而消失。因此**每次 Host 启动都必然再次命中、再次 resume、再次注入、再次挂死**——杀进程重启多少次都无效，只有停用插件才能断开。
- **越界改写会话**：`resume` 会向会话日志追加中断收尾事件，`followup` 会写入一条 user 消息。审计（按注入消息的原文开头做唯一指纹）确认向 **2 个会话**写入过注入消息，时间与插件启动时刻吻合。

### 设计层面的错误

需求 G1 写的是「崩溃后下次启动自动续跑」，实现把它理解成「自动让模型继续工作」。这是概念混淆：

- 「续跑」应当是**把崩溃会话恢复成可继续的状态**，并把「上次是异常中断」这个事实**告诉用户**，由用户决定是否继续。
- 让后台插件代替用户决定「继续干活」并自动触发模型推理，超出了插件应有的权限边界，且在最需要人监督（结果不明的工具调用可能有副作用）的时刻恰恰没有人在场。

需求 G5「不碰正在运行的会话」本意是安全护栏，但它只防住了「已知的 live」，没有防住「判定与真实状态不一致」与「插件本身不该触发推理」这两层问题。

## 结论与约束

- 本插件的需求（[requirement.md](requirement.md)）作为用户规格**原样保留**，供将来参考。
- **不要按原机制重新实现**。具体要求：
  - 插件**不得**自动 `resume` + `followup`，不得触发任何模型推理轮次；
  - 若将来再做，只允许「只读扫描 + 在界面上列出哪些会话上次是异常中断」，把「是否继续」交给用户点击；
  - 任何会自动产生模型调用与工具执行的后台行为，必须在实现前单独评审其失败模式与无人值守风险。
- 受影响的那 2 个会话中的注入消息属于历史数据，未作修改。
